# The Agency（agency-agents）开发文档

本文档面向**贡献者与维护者**：说明仓库结构、构建/安装脚本、智能体约定与扩展集成时的注意点。终端用户使用方式见 [用户使用文档](./用户使用文档.md)。

---

## 1. 项目性质与架构概览

- **核心资产**：各目录下的智能体源文件，为 **Markdown**，带 **YAML frontmatter**。  
- **无应用服务**：本仓库不是可运行的 Web 后端；价值在于可被拷贝、转换并注入到多种「智能体宿主」工具中。  
- **生成物**：`scripts/convert.sh` 将源文件转为各工具格式，输出到 **`integrations/<tool>/`**；`scripts/install.sh` 只负责把 `integrations/` 里的产物拷到用户环境或当前项目路径。

```
agency-agents/
├── academic/ design/ engineering/ game-development/ …   # 智能体源 .md
├── strategy/                    # NEXUS / playbook / runbook（策略文档）
├── examples/                    # 多智能体协作示例输出
├── integrations/                # convert 生成物 + 各工具 README
├── scripts/
│   ├── convert.sh              # 源 → integrations
│   ├── install.sh              # integrations → 本机/项目
│   └── lint-agents.sh          # 源文件静态检查
├── CONTRIBUTING.md
├── CONTRIBUTING_zh-CN.md
└── README.md
```

## 2. 智能体源文件规范

### 2.1 Frontmatter（必填字段）

与 [CONTRIBUTING_zh-CN.md](../CONTRIBUTING_zh-CN.md) 一致，至少包含：

```yaml
---
name: ...
description: ...
color: ...
---
```

部分文件还包含 `emoji`、`vibe` 等扩展字段，供转换脚本或展示使用；**以现有同类文件为准**保持风格一致。

### 2.2 正文结构（建议）

贡献指南中推荐的章节包括：身份与记忆、核心使命、关键规则、技术交付物、工作流程、沟通风格、成功指标等。完整清单见 CONTRIBUTING_zh-CN 中「智能体设计规范」。

### 2.3 文件命名与分类

- 路径模式：`<category>/<category>-<slug>.md`（与现有文件保持一致）。  
- 新增智能体时选择最贴近的 `category` 目录；确无合适类目时可考虑 `specialized/` 或在讨论中提议新目录。

### 2.4 静态检查：`lint-agents.sh`

```bash
./scripts/lint-agents.sh              # 扫描脚本内配置的目录下所有智能体
./scripts/lint-agents.sh path/to/file.md   # 仅检查指定文件
```

当前脚本会校验：

- 是否存在闭合的 YAML frontmatter  
- `name` / `description` / `color` 是否出现  
- 是否包含一定长度的正文  
- 对若干推荐章节做 **WARN**（不阻断）

提交 PR 前建议在修改过的文件上运行该脚本。注意：`lint-agents.sh` 内声明的扫描目录列表与 `convert.sh` 中的 `AGENT_DIRS` **可能不完全一致**；若你在 `academic/`、`sales/` 等目录增删文件，请同时关注 lint 是否覆盖该路径，必要时在脚本中补齐（需单独 PR 讨论）。

### 2.5 中文全目录文档：`generate_agent_catalog_zh.py`

用于重新生成 [智能体全目录与组合流程.md](./智能体全目录与组合流程.md)（含机器翻译的 **中文阐释** 字段）。依赖 `deep-translator`（需自备 venv 安装）。翻译结果缓存于 `docs/.agent-catalog-zh-cache.json`（已列入 `.gitignore`）。源智能体变更后删除缓存或等待脚本按文件 mtime 自动更新对应条目即可。

```bash
python3 -m venv /tmp/agency-catalog-venv
/tmp/agency-catalog-venv/bin/pip install deep-translator
/tmp/agency-catalog-venv/bin/python3 scripts/generate_agent_catalog_zh.py
```

## 3. `convert.sh`（生成集成产物）

**作用**：读取各分类目录中的智能体 Markdown，写入 **`integrations/<tool>/`**，不修改用户主目录。

**常用调用**：

```bash
./scripts/convert.sh                  # 全部工具
./scripts/convert.sh --tool cursor    # 仅 Cursor
./scripts/convert.sh --parallel       # 多工具并行（输出顺序可能乱序）
./scripts/convert.sh --help
```

**`convert.sh` 中维护的源目录列表**（以脚本内 `AGENT_DIRS` 为准）包括：`academic`、`design`、`engineering`、`game-development`、`marketing`、`paid-media`、`sales`、`product`、`project-management`、`testing`、`support`、`spatial-computing`、`specialized`。

**支持的工具**（以 `--help` 与脚本头部注释为准）：如 `antigravity`、`gemini-cli`、`opencode`、`cursor`、`aider`、`windsurf`、`openclaw`、`qwen`、`kimi` 等。

新增工具集成时，通常需要：

1. 在 `convert.sh` 中增加转换逻辑与输出目录约定；  
2. 在 `install.sh` 中增加安装目标路径与检测逻辑；  
3. 在 `integrations/<new-tool>/` 下补充 README，并在 [integrations/README.md](../integrations/README.md) 登记。

---

## 4. `install.sh`（安装到本机或项目）

**作用**：从 `integrations/` 读取已生成文件，复制到各工具约定位置（如 `~/.claude/agents`、`./.cursor/rules` 等）。

**常用调用**：

```bash
./scripts/install.sh
./scripts/install.sh --tool cursor
./scripts/install.sh --no-interactive --tool all
./scripts/install.sh --parallel --jobs 4
```

**注意**：

- 项目级工具需在**目标项目根目录**执行，以便写入相对路径配置。  
- 若 `integrations/` 缺失或过期，应先运行 `convert.sh`。  
- Windows 下建议使用 Git Bash 或 WSL（脚本头部注释有说明）。

## 5. 策略与示例目录（非 convert 源）

- **`strategy/`**：NEXUS 流水线、阶段 playbook、runbook、协调模板等，供用户在会话中复制提示词使用；**不是** `convert.sh` 默认扫描的智能体根目录。  
- **`examples/`**：展示多智能体协作成果的示例 Markdown，供文档与社区引用。  

若新增「可执行策略文档」，优先放入 `strategy/` 或 `examples/`，并在 README 或本 docs 中增加索引链接。

## 6. 贡献流程（摘要）

详细步骤、PR 模板与设计原则以 **[CONTRIBUTING_zh-CN.md](../CONTRIBUTING_zh-CN.md)**（或英文 [CONTRIBUTING.md](../CONTRIBUTING.md)）为准。摘要如下：

1. Fork 仓库并创建分支。  
2. 在合适目录添加或修改 `.md` 智能体文件，遵循结构与风格指南。  
3. 本地用真实任务试跑；运行 `./scripts/lint-agents.sh`（及相关文件）。  
4. 若改动影响集成产物，运行 `./scripts/convert.sh`（全量或对应 `--tool`），将 **`integrations/` 的合法变更**一并提交（若项目维护策略要求生成物与源同步）。  
5. 发起 PR，标题与说明清晰，附上测试说明。

是否与主仓库同步提交 `integrations/` 下生成文件，以当前仓库惯例与 PR 模板为准；如有疑问可先查看近期已合并 PR 的做法。
