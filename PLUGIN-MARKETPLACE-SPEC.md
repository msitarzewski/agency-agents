## 0. TL;DR

- **Architecture B wins, with one correction.** One small `.claude-plugin/plugin.json` manifest is added inside each of the 17 existing division folders (plugin root = the division folder itself). Zero `.md` files move, duplicate, or rename.
- The user-sketch Architecture B used `"agents": ["./"]`. **That does not validate.** The `agents` field accepts **explicit `.md` file paths, not directories**. So the generator enumerates every frontmatter agent `.md` per division.
- Architecture A (`../` parent traversal) is **impossible**: `claude plugin validate` rejects `..` outright as a path-traversal attempt, and even if it didn't, Claude Code copies the plugin directory into a cache at install, so files outside the plugin root would not exist at runtime. The symlink workaround is fragile on Windows (this repo's contributors and CI story) and requires `.gitattributes` + elevated `mklink` privileges. Rejected.
- **One plugin per division (17 plugins), not one monolithic plugin.** Matches divisions.json's "division = installable team" model, which the repo already implements in `install.sh --division`, the app's one-click team deploy, and `strategy/runbooks.json`.
- New machinery follows the existing repo pattern: `scripts/build-marketplace.py` (mirrors `scripts/build-hermes-plugin.py`) + `scripts/check-plugin-marketplace.sh` (mirrors `scripts/check-tools.sh`) + `.github/workflows/check-plugin-marketplace.yml` (mirrors `check-divisions.yml`).
- **No change** to `divisions.json`, `tools.json`, `scripts/check-divisions.sh`, `scripts/convert.sh`, `scripts/install.sh`, `.gitignore`, or `.gitattributes`. The marketplace is a *distribution* mechanism consumed by the target clients directly, not an install target of this repo's own convert/install pipeline — so it stays orthogonal to `tools.json` and `install.sh`.
- The manifests **must be committed to git** (marketplace installs clone the repo and run no build step). They are generated by script but committed, exactly like `integrations/*/README.md` is a committed per-integration artifact today. A CI drift-check keeps them in sync with the roster.

## 1. The empirical question, resolved

> Does the `agents`/`skills` path field in plugin.json allow `../` to reference a directory OUTSIDE the plugin root, or is it restricted to the plugin root and its subdirectories?

**Resolution: `../` is forbidden by the validator, and the install-time cache copy makes it impossible regardless.** Tested empirically with Claude Code **v2.1.201** on this machine (Windows), plus confirmed against the current official docs.

### 1.1 Direct test results

Throwaway plugins were created under a temp dir and validated with `claude plugin validate`:

| `plugin.json` `agents` value | Result | Output |
|---|---|---|
| `["../../outside"]` | **FAILED** (exit 1) | `✘ agents: Invalid input`<br>`✘ agents[0]: Path contains ".." which could be a path traversal attempt: ../../outside` |
| `["./"]` | **FAILED** (exit 1) | `✘ agents: Invalid input` |
| `["./agents/"]` (directory) | **FAILED** (exit 1) | `✘ agents: Invalid input` |
| `["./demo-agent.md"]` (file) | **PASSED** (exit 0) | `✔ Validation passed with warnings` (author/description warnings only) |
| `["./engineering-frontend-developer.md", "./engineering-backend-architect.md"]` (sibling files, Architecture B shape) | **PASSED** | `✔ Validation passed with warnings` |
| Same, but with a nested subdir agent: `["./game-designer.md", "./unity/unity-architect.md"]` | **PASSED** | `✔ Validation passed with warnings` |

Two hard facts fall out:

1. **`..` is rejected** at validation time with an explicit path-traversal error.
2. **`agents` takes *files*, not directories.** The `skills` field accepts directories (`"./custom/skills/"`), but `agents` requires individual `.md` agent files. This corrects the Architecture B sketch: `"agents": ["./"]` fails, so we must enumerate the `.md` files.

### 1.2 Install-time cache copy makes traversal moot

From the current Claude Code docs (plugins-reference, "Path traversal limitations"):

> **Installed plugins cannot reference files outside their directory. Paths that traverse outside the plugin root (such as `../shared-utils`) will not work after installation because those external files are not copied to the cache.**

And from plugin-marketplaces:

> when users install a plugin, Claude Code **copies the plugin directory to a cache location**. This means plugins can't reference files outside their directory using paths like `../shared-utils`, because those files won't be copied.

So even a hypothetical build that accepted `..` would break for marketplace users, because the referenced files are not inside the plugin root that gets copied to `~/.claude/plugins/cache/`.

### 1.3 End-to-end proof of the chosen architecture

A full throwaway marketplace mirroring the proposed layout was created and exercised end-to-end in a sandboxed config (`CLAUDE_CONFIG_DIR` + `CLAUDE_CODE_PLUGIN_CACHE_DIR`):

```text
real-mk/
  .claude-plugin/marketplace.json          # lists ./engineering and ./marketing
  engineering/.claude-plugin/plugin.json   # agents: ["./engineering-frontend-developer.md", ...]
  engineering/engineering-*.md
  marketing/.claude-plugin/plugin.json
  marketing/marketing-growth-hacker.md
```

```bash
$ claude plugin validate ./real-mk
✔ Validation passed with warnings

$ claude plugin marketplace add ./real-mk
✔ Successfully added marketplace: agency-agents (declared in user settings)

$ claude plugin install agency-engineering@agency-agents
✔ Successfully installed plugin: agency-engineering@agency-agents (scope: user)
```

The cache tree confirmed the copy behavior:

```text
~/.claude/plugins/cache/agency-agents/agency-engineering/1.0.0/
  .claude-plugin/plugin.json
  engineering-frontend-developer.md
  engineering-backend-architect.md
```

Relative-path marketplace `source` values resolved against the **marketplace root** (repo root), and the whole division directory — manifest plus `.md` files — was copied into the versioned cache. All references stay inside the plugin root. This is the design the spec builds on.

### 1.4 Architecture decision and justification

| | Architecture A (`../`) | Architecture B (in-division manifest) |
|---|---|---|
| Validator accepts it | **No** — rejected as path traversal | **Yes** — validated (1.1, 1.3) |
| Survives cache copy | **No** — external files not copied | **Yes** — all refs inside plugin root |
| New top-level dir needed | `plugins/` (touches `check-divisions.sh` `NON_DIVISION_DIRS`) | None (dot-prefixed dirs only) |
| Files inside division dirs | 0 | 1 small `.json` per division |
| Windows-safe symlinks | N/A — no symlinks used | N/A |
| `.md` files moved/duplicated/renamed | None | None |

**Decision: Architecture B**, with the correction that `agents` is an explicit file list. There is no scenario under which Architecture A is viable for marketplace distribution.

A hybrid "Architecture A via symlinks" was considered (a `plugins/<division>/` dir whose `agents` list symlinks back to `../../engineering/*.md`). The Claude docs explicitly sanction symlinks that resolve elsewhere within the marketplace (they are dereferenced into the cache). It was rejected because: (a) this repo has no symlink precedent in `.gitattributes`; (b) on Windows — where much of this project's contribution happens — checked-in symlinks are disabled by default and become broken text files for contributors who haven't enabled Developer Mode; (c) `check-divisions.sh` would need a `NON_DIVISION_DIRS` edit; (d) the upside (0 files in division folders) is bought at disproportionate maintenance risk versus one generated 2 KB manifest per division.

## 5. One plugin per division (17) vs one monolithic plugin

**Recommendation: one plugin per division — 17 plugins, one marketplace.**

Justification:

1. **divisions.json's own model is "division = installable team".** `scripts/install.sh` has `--division` selection; the Agency Agents app ships one-click *team* deploy; `strategy/runbooks.json` builds teams from division rosters. A per-division plugin is the marketplace-shaped equivalent of that existing granularity.
2. **Install surface.** A user who only wants engineering (58 agents) installs `agency-engineering@agency-agents` and gets exactly that. A monolithic `agency-agents` plugin would force-install all 270 agents and enable them at once, with no per-team control (enable/disable is per-plugin in both Claude Code and VS Code).
3. **Namespacing.** Plugin agents appear scoped as `<plugin>:<agent>` (e.g. `agency-engineering:frontend-developer`). Per-division plugins keep the @-mention typeahead navigable; a 270-agent monolith floods it.
4. **Update granularity and cache.** Each division versions independently in `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`; a monolith would re-copy 270 files on every commit-triggered update.
5. **No cost for 17 manifests.** They are generated from a single source of truth, so the "maintenance" argument against many plugins is zero-touch.

The only real cost of 17 plugins is marginally more entries in the marketplace file and 17 small files in the repo — both generated.

## 6. Generator and validator scripts

### 6.1 `scripts/build-marketplace.py` (new — mirrors `scripts/build-hermes-plugin.py`)

Stdlib-only Python 3, no third-party deps (repo precedent: `build-hermes-plugin.py`, `check-runbooks.sh`).

Behavior:

1. Reads `divisions.json` (single source of truth for the division set — same "derive, don't hardcode" rule as `build-hermes-plugin.py`).
2. For each division, walks `<div>/**/*.md`, keeping only files whose first line is `---` (frontmatter) — identical frontmatter gate to `convert.sh` and `has_agent_file` in `check-divisions.sh`.
3. Emits `<div>/.claude-plugin/plugin.json`:
   - `name`: `agency-<division>`
   - `displayName`: `Agency — <division label>`
   - `description`: from the division label + agent count
   - `author.name`: `Agency Agents`
   - `agents`: `./`-prefixed paths relative to the division root, subdirectories preserved (`./unity/unity-architect.md`), sorted by path. **No `version`** (commit-SHA versioning).
4. Emits `.claude-plugin/marketplace.json`: name `agency-agents`, owner, and one entry per division with `source: "./<division>"` and a short description.
5. Refuses to emit an `agents` entry that does not exist, is not `./`-prefixed, or is not inside the division root.

CLI (matching hermes precedent):

```bash
python3 scripts/build-marketplace.py                          # write in place (default)
python3 scripts/build-marketplace.py --out <tmp>              # build to a scratch dir (used by the checker)
```

Writes with UTF-8, LF line endings, trailing newline — byte-stable so the drift check is exact.

### 6.2 `scripts/check-plugin-marketplace.sh` (new — mirrors `scripts/check-tools.sh`)

Bash 3.2 + coreutils + python3 (already required by `check-runbooks.sh`); no jq. Fails the build if **any** of the following disagree:

1. **Drift:** `build-marketplace.py --out <tmp>` output must byte-match the committed `.claude-plugin/marketplace.json` and every `<div>/.claude-plugin/plugin.json`. This is the backstop that a new agent or division cannot go out without its manifest (no path filters to dodge — the workflow runs on every PR, see §7).
2. **Structure:** marketplace JSON parses; `name` is kebab-case and not on Claude's reserved-name list; `owner.name` present; every plugin entry has `name` + `source`; `source` starts with `./` and contains no `..`.
3. **Coverage (both directions):** the marketplace plugin-name set == the divisions.json division set (each `agency-<division>`), and each `source` resolves to a directory containing `.claude-plugin/plugin.json`.
4. **Path hygiene:** every `agents[]` value starts with `./`, contains no `..`, and names a real file within the plugin root.

The script stays dependency-free so it runs identically on macOS and CI — mirroring the "no jq" rule in `check-divisions.sh`/`check-tools.sh`.

### 6.3 Optional authoritative validation

The real authority is `claude plugin validate`. Verified during this spec: `claude plugin validate .` at the marketplace root validates the marketplace **and** every listed plugin's `plugin.json` (it reported per-plugin warnings in test). A CI step runs it with `--strict` (treats warnings as errors), installed ad hoc so the repo gains no dependency:

```bash
npx -y @anthropic-ai/claude-code plugin validate . --strict
```

This is the one place the repo would invoke the Claude Code runtime; the shell checker above guarantees structural correctness even if the `npx` step is dropped for CI time/cost.

## 7. CI wiring

New workflow `.github/workflows/check-plugin-marketplace.yml`, mirroring `check-divisions.yml` (no path filter, runs on every PR plus push to main — a new division or renamed agent must trip it even if nobody touched the manifests):

```yaml
name: Check Plugin Marketplace Consistency

# Runs on every PR (no path filter on purpose): a new division or agent must
# trip this check even when nobody touched .claude-plugin/ or the build script.
on:
  pull_request:
  push:
    branches: [main]

jobs:
  check-plugin-marketplace:
    name: marketplace manifests match the roster
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Validate generated marketplace manifests
        run: |
          chmod +x scripts/check-plugin-marketplace.sh
          ./scripts/check-plugin-marketplace.sh

      - name: Validate against Claude Code plugin rules
        run: npx -y @anthropic-ai/claude-code plugin validate . --strict
```

No change to any existing workflow.

## 8. Changes to existing files

| File | Change | Why |
|---|---|---|
| `divisions.json` | **None** | Still the single source of truth for the division set; the generator reads it. |
| `tools.json` | **None** | The marketplace is a *distribution channel* consumed by the target clients (`/plugin marketplace add`, VS Code `chat.plugins.marketplaces`), **not** a per-tool install target of this repo's convert/install pipeline. `installKind` (`per-agent\|roster\|plugin`) is the install *mechanism* for `install.sh`; a marketplace entry would need dest dirs, detection, and an `install_<tool>` that contradict how users install it. Adding `installKind: "marketplace"` would broaden the schema and ripple into `check-tools.sh`, the app, and `install.sh` for zero benefit. Decision: **orthogonal to tools.json**; document it in the new README instead. |
| `scripts/check-divisions.sh` | **None** | Both new dir kinds are dot-prefixed; `actual_dirs()` skips them and only inspects top-level names. No `NON_DIVISION_DIRS` edit needed (unlike Architecture A's `plugins/`). |
| `scripts/convert.sh` | **None** | Marketplace manifests are committed, generated artifacts for the clients; they are not per-agent conversion output. Wiring `convert.sh --tool` would force a `tools.json` entry (check-tools.sh requires every converter to exist there) — exactly what §8 avoids. |
| `scripts/install.sh` | **None** | Users install via `/plugin install` / VS Code, never `./scripts/install.sh --tool marketplace`. `ALL_TOOLS` must stay in lockstep with tools.json (check-tools.sh). |
| `scripts/lint-agents.sh` | **None** | Only processes `.md` files. |
| `scripts/check-runbooks.sh` | **None** | Glob is `git ls-files "*/*.md"`; manifests are `.json`. |
| `.gitignore` | **None** | **Critical: the manifests must NOT be gitignored.** Marketplace installs clone the repo and run no build step; a gitignored manifest means a broken plugin for every consumer. They are committed, like `integrations/*/README.md`. |
| `.gitattributes` | **None** | No symlinks introduced (Architecture A symlink variant rejected). |

Also note the marketplace under "Things we'll always close" guidance is fine because manifests are small committed artifacts, unlike converted agent output. |

### The "committed generated output" tension, decided

CONTRIBUTING.md currently says committed build output is always closed. The marketplace manifests are generated yet **must be committed** — an install-time requirement, not a convenience. This is the same status as `integrations/*/README.md` (committed per-integration artifact) rather than the converted agent files (gitignored). The spec keeps this exception explicit and narrow: only the two `.claude-plugin/` file kinds and the scripts/docs are committed; no `.md` is ever generated or duplicated.

## 10. How a user consumes this (worked examples)

### 10.1 VS Code (Agent Plugins, Preview)

VS Code's `chat.plugins.marketplaces` accepts `owner/repo` shorthand, full git URL, SCP-style, or `file://`, and auto-detects `.claude-plugin/plugin.json` as the Claude plugin format. In `settings.json`:

```json
{
  "chat.plugins.enabled": true,
  "chat.plugins.marketplaces": ["Marinski/agency-agents#plugins"]
}
```

Then:

1. Open the **Extensions** view (`Ctrl+Shift+X`), search `@agentPlugins`.
2. Accept the marketplace trust prompt on first install.
3. Find **Agency — Engineering**, select **Install** (user profile), enable it.

> **Ownership (settled):** docs and the publish target use `Marinski/agency-agents`
> (the fork; origin), and consumers target the `#plugins` dist branch — see the
> supersede banner at the top of this file.

### 10.2 Claude Code

In a Claude Code session:

```text
/plugin marketplace add Marinski/agency-agents#plugins
/plugin install agency-engineering@agency-agents
/reload-plugins
```

Non-interactive CLI equivalents (same behavior, scriptable):

```bash
claude plugin marketplace add Marinski/agency-agents#plugins
claude plugin install agency-engineering@agency-agents     # default scope: user
claude plugin install agency-engineering@agency-agents --scope project
```

To install several divisions at once, run `install` per plugin; the marketplace is added once. Installed agents appear scoped as `agency-engineering:<agent>` in the @-mention typeahead and are auto-updatable (Claude Code re-pulls the marketplace and treats each new commit as a new version because `version` is omitted).

> `owner/repo` shorthand clones over SSH by default in Claude Code; HTTPS-only users set `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1`.

### 10.3 Optional: recommend the marketplace from the repo itself

For teams that clone this repo (or an org that mirrors it), workspace plugin recommendations work in both tools via `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "agency-agents": { "source": { "source": "github", "repo": "Marinski/agency-agents#plugins" } }
  },
  "enabledPlugins": {
    "agency-engineering@agency-agents": true
  }
}
```

Marked optional — out of scope for the initial change, since committing it would make the repo's own workspace self-recommend its marketplace.

## 11. Risks / open questions (called out, not assumed)

1. **VS Code's `agents` field semantics (highest-risk open question).** VS Code's own agent-plugins doc (fetched 2026-07-29) describes `plugin.json` `agents` as "Path(s) to **agent directories**. Defaults to `agents/`", while Claude Code empirically requires **files** (this spec's §1.1). VS Code links to the Claude marketplace schema for the full contract and auto-detects the Claude format, but the two descriptions genuinely diverge. **If VS Code 1.110 treats each `agents` value as a directory, per-file listings may fail to load in VS Code.** This cannot be resolved from docs alone; the implementation must include a hands-on VS Code install test of one generated plugin. Fallbacks if it fails: (a) confirm VS Code actually shares Claude's file-list loader (likely, since it delegates to the same marketplace schema); (b) ship an `agents/` directory per division containing the listed `.md` files via the **symlink-dereference** path Claude documents for marketplace-local sharing — rejected for now, revisited only if the test fails; (c) document VS Code as "agents not yet loaded; use Claude Code / Copilot CLI" until upstream unifies. This is the #1 item to verify during implementation, before marketing the VS Code path.
2. **Agent frontmatter `name` is Title Case with spaces** (e.g. `name: Frontend Developer`), and includes Agency-specific fields (`color`, `emoji`, `vibe`, `services`) that Claude Code ignores. `claude plugin validate` accepts this (tested in §1.1/§1.3), but the exact @-mention scoped-name (`agency-engineering:frontend-developer` vs a slugified `name`) is a runtime behavior not observable via `validate`. Verify in a real session during implementation; if scoped names are ugly, consider whether plugin agents should also carry a kebab-case `name` — but that would mean touching source `.md` frontmatter, which this spec forbids, so the fallback is documenting the observed naming.
3. **GitHub owner mismatch** — **resolved:** docs and the publish target use `Marinski` (the fork, origin); consumers target `Marinski/agency-agents#plugins`. Only the repo's pre-existing upstream branding (badges, app links) still uses `msitarzewski`.
4. **`npx @anthropic-ai/claude-code plugin validate --strict` in CI** downloads the CLI on every run. If that is too slow/costly, the structural drift-check (§6.2) is still a hard gate; the `npx` step can be marked allow-fail or removed. The `--strict` flag means currently-unrecognized fields (none planned) would surface as errors rather than warnings.
5. **New agent naming for future divisions.** The marketplace/plugin `name` derives from the division key (`agency-<division>`). A future division whose key is not kebab-case (e.g. contains `_`) would need slugification in the generator; the checker should reject non-kebab plugin names so this cannot slip through silently.
6. **Claude reserved-name collision.** `agency-agents` is clear today, but the reserved-name list is enforced on every marketplace load and is occasionally extended. The checker (§6.2) should hard-code the current reserved list so a future collision fails CI rather than silently breaking installs.
7. **VS Code `@agentPlugins` discovery requires `chat.plugins.enabled: true`** (Preview gate, org-manageable). Docs should state this, as a plugin "not appearing" is the top VS Code troubleshooting item.
8. **17 plugins = 17 `enabledPlugins` keys** if a team wants all divisions in `.claude/settings.json`. Acceptable; users who want "everything" still can't get it with one install line. If this becomes a real complaint, a `agency-all` meta-plugin (one extra generated manifest listing every division's agents) is a trivial generator follow-up — deliberately out of scope now.
